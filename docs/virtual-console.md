# Virtual Console resource/configuration layer

Added 2026-08-19, on top of the existing Phase 1-10 + compatibility-audit
runtime (see `CLAUDE.md` for that history). This document covers ONLY the
new resource-loading/configuration layer described below — it does not
change or re-document anything about SWF parsing, AVM1, rendering, hit-
testing, or event dispatch, all of which are reused completely unchanged.

## 1. Architecture

```
3DS application (nintendo3ds_main.cpp)
      |
      v
   RomFS (embedded in flash3ds_3ds.3dsx, see Nintendo3DSRomfs)
      |
      +-- game.swf
      |
      +-- config.ini
      |
      v
   GamePackage (src/vc/GamePackage.h)
      |
      +-- GameConfig (src/vc/GameConfig.h, backed by IniDocument)
      |
      v
   SwfLoader::loadSwf() -- UNCHANGED, existing (Phase 1)
      |
      v
   MovieClipInstance / ScriptEnvironment -- UNCHANGED, existing (Phase 5+)
      |
      +-- AVM1, MovieClip, ButtonInstance, hit testing, EventDispatcher,
      |   InputState, SceneRenderer, ExternalInterface -- ALL UNCHANGED
      |
      v
   Nintendo3DSInput -- unchanged hid-polling/edge logic; the TARGET
                        InputState key code per physical button and the
                        touch/mouse enabled flags are now configurable
                        (vc::InputMapping, part of GameConfig)
```

The new code (`src/vc/*`, `src/platform/Nintendo3DSRomfs.*`) implements
**only** resource loading, config parsing, and input-mapping configuration.
It does not reimplement or duplicate any SWF/AVM1/renderer/input logic —
see "Architectural rules" below and each file's own header comment for the
specific "why."

## 2. RomFS layout

```
romfs/
├── config.ini
└── game.swf
```

This directory is checked into the repository (`romfs/config.ini` +
`romfs/game.swf`, the latter a small clean-room demo SWF generated by
`tools/gen_3ds_demo_swf.py --swf-out romfs/game.swf` — see that script)
and embedded directly into `flash3ds_3ds.3dsx` at build time via
3dsxtool's own `--romfs=` flag (see `CMakeLists.txt`'s
`FLASH3DS_BUILD_3DS` block). **No CIA packaging, no SD-card file I/O, no
libctru `romfsInit()`** — see section 4 for why.

Both files are read at RESOLVED root, matching the layout above exactly.
There is no subdirectory support — not needed for two files, and the
Virtual Console spec's own layout doesn't call for it.

## 3. config.ini syntax

```ini
[game]
swf=game.swf

[input]
A=ENTER
B=ESCAPE
X=SPACE
Y=SHIFT
L=L
R=R
ZL=Z
ZR=V
START=ENTER
SELECT=ESCAPE
CSTICK_UP=I
CSTICK_DOWN=K
CSTICK_LEFT=J
CSTICK_RIGHT=M

[touch]
enabled=true
screen=bottom

[mouse]
enabled=true
```

This is exactly `romfs/config.ini`'s own committed content, and exactly
what `vc::GameConfig::defaults()` produces when config.ini is missing
entirely — the two are guaranteed to never drift apart, since
`defaults()` is literally `fromIniText("")` (an empty document has no
overrides to apply, so every field keeps its own hardcoded default; see
`src/vc/GameConfig.cpp`).

Grammar (`src/vc/IniDocument.h`): `[section]` headers, `key=value` pairs
(whitespace-trimmed on both sides), `;` or `#` line comments, blank lines
ignored. Deliberately tiny — no third-party INI library, matching "keep
the parser intentionally small" — the whole grammar is ~60 lines
(`IniDocument.cpp`).

### Error handling

| Condition | Behavior |
|---|---|
| config.ini missing | Use documented defaults (table above) — `GameConfig::defaults()`. |
| config.ini present but empty | Identical to "missing" — `fromIniText("")` either way. |
| Unknown `[section]` | Stored, never read by `GameConfig`, otherwise ignored. |
| Unknown key in a known section | Same — ignored. |
| Invalid value for a known key (e.g. `A=NOT_A_REAL_KEY`, `enabled=maybe`) | That ONE field falls back to its own default; every other field parses normally. Logged via `LOG_WARN("VC", ...)`. |
| Duplicate `key=` in the same section | Last one wins. |
| Malformed line (no `=`, not a comment/header) | Recorded, skipped, logged; parsing continues. |
| `game.swf` (or whatever `[game] swf=` names) missing | `GamePackage.movie->valid == false`, `errorMessage == "Resource not found: <name>"`. The 3DS entry point logs this and exits cleanly (`return 1`) — never a silent freeze/infinite loop. |
| Invalid/malformed SWF (present, but not parseable) | `SwfLoader`'s own existing, well-established error reporting (`movie->valid == false`, a specific `errorMessage`) — unchanged, reused as-is. |

## 4. Why a bespoke RomFS reader instead of libctru's `romfsInit()`

This from-source toolchain build (see `docs/3ds-toolchain.md`) excludes
`romfs_dev.c` for the exact same reason `archive_dev.c`/`console.c` are
excluded: it needs the full `sys/iosupport.h` device-table framework,
which isn't available with this project's stock (non-devkitARM-patched)
newlib. Calling `romfsInit()`/`romfsMountSelf()` would fail to **link**,
not just misbehave at runtime.

`src/platform/Nintendo3DSRomfs.h/.cpp` reimplements only the narrow
subset of `romfsMountSelf()`'s own logic that does NOT need iosupport:
locate this running `.3dsx`'s own file on the SD card (from `argv[0]`),
open it directly via `FSUSER_OpenFileDirectly` (an ordinary FS-service
call, unaffected by the exclusion), read the 3DSX header to find the
embedded RomFS section's byte offset, then read that section's own
header/directory-table/file-table (the public RomFS format, via
`<3ds/romfs.h>`'s own structs) directly via `FSFILE_Read` — entirely
without installing any devoptab/newlib virtual-filesystem device.
Deliberately scoped to a flat root directory (linear scan over the file-
sibling chain), matching this project's own two-file `romfs/` layout —
not a general-purpose RomFS implementation.

**Verified without hardware/emulator access** (same constraint Phase 10
had): the embedded RomFS section's raw bytes were manually parsed with an
independent Python script and cross-checked byte-for-byte against
`Nintendo3DSRomfs::readFile()`'s own algorithm and against the source
`romfs/config.ini`/`romfs/game.swf` files on disk — both matched exactly.
The `.3dsx`'s undefined-symbol list after linking is unchanged from Phase
10's own prior verification (only the same 8 weak libctru/C++-runtime
hooks) — confirming every new FS-service call resolved correctly. See
section 7 for the full command transcript.

**3dsxtool's own `--romfs=` quirk:** it unconditionally requires an
`--smdh=` file whenever `--romfs=` (or `--smdh=`) is used at all — reading
`3dstools/src/3dsxtool.cpp`'s `WriteExtHeader()` shows it calls
`fopen(smdhFile, "rb")` with no null check, so `--romfs=` alone would
crash. 3dsxtool does not parse or validate the SMDH's contents at all
(just its size, for offset math) — so `tools/gen_placeholder_smdh.py`
generates a minimal, correctly-**sized** (0x36C0 bytes, verified) but
purely cosmetic placeholder (solid-color icon, generic title text) at
build time. This is **not** a CIA banner/icon asset and has nothing to do
with CIAToolsR's own separate icon/banner requirements — see section 8.

## 5. Input mapping

`vc::InputMapping` (`src/vc/GameConfig.h`) holds one `int` per remappable
physical button (A/B/X/Y/L/R/ZL/ZR/START/SELECT/CSTICK_UP/CSTICK_DOWN/
CSTICK_LEFT/CSTICK_RIGHT), reusing
`runtime::InputState::KeyCode` for every named token (`ENTER`, `ESCAPE`,
`SPACE`, `SHIFT`, ... — the exact same enum `InputState`, AVM1's `Key`
object, and every other existing consumer already use) plus direct
pass-through for a single printable ASCII character (`"L"` → `'L'`,
matching the convention `Nintendo3DSInput` already used before this layer
existed). **No parallel key-code system was introduced.**

`Nintendo3DSInput` (`src/platform/Nintendo3DSInput.h/.cpp`) gained a
`const vc::InputMapping&` constructor parameter (defaulted, so every
existing call site keeps compiling). It still owns 100% of the actual
libctru `hid` polling/rescaling logic unchanged — the only thing that
became configurable is which `InputState` key code each physical button's
held-state gets written to, and whether touch/mouse feed `InputState` at
all. D-Pad → arrow keys is NOT configurable (no natural alternative
binding exists, and the spec doesn't ask for it).

**One subtlety fixed while wiring this up:** the documented default maps
both A and START to `Key.ENTER` (and B/SELECT to `Key.ESCAPE`) — the
ORIGINAL hardcoded code combined these with a single OR'd `setKeyDown`
call. A naive per-button rewrite (`setKeyDown(mapping.aKeyCode, ...)` then
`setKeyDown(mapping.startKeyCode, ...)`) would let the second call
silently stomp the first whenever two physical buttons share a target
code. `poll()` now explicitly OR-merges every physical button's flag per
DISTINCT target code before calling `setKeyDown()` (see that function's
own comment) — preserving "either button presses the logical key" exactly
like the original hardcoded version did.

**One deliberate behavior change, clearly flagged:** X/Y's documented
default changed from literal ASCII `'X'`/`'Y'` (the original hardcoded
value) to `Key.SPACE`/`Key.SHIFT`, to match this layer's own documented
default `config.ini` (AS2 content is far more likely to test
`Key.SPACE`/`Key.SHIFT` than literal `'X'`/`'Y'` character codes). L/R's
default (`'L'`/`'R'`) is unchanged.

**ZL/ZR/C-Stick (2026-08-24):** the New-3DS-only extra shoulder buttons
and second analog stick are mapped exactly like every button above — same
`applyKeyMapping()` parsing path, same `Nintendo3DSInput` OR-merge table.
ZL/ZR default to `'Z'`/`'V'` (arbitrary, documented, rebindable — see
`GameConfig.h`). The C-Stick is exposed by libctru as four independent
digital held-bits (`KEY_CSTICK_UP`/`DOWN`/`LEFT`/`RIGHT`), **not** merged
into `KEY_UP`/`DOWN`/`LEFT`/`RIGHT` the way the Circle Pad is — so it polls
like four more ordinary buttons rather than a stick with its own analog
reading, and each direction gets its own `CSTICK_UP`/`CSTICK_DOWN`/
`CSTICK_LEFT`/`CSTICK_RIGHT` config.ini key (default `'I'`/`'K'`/`'J'`/
`'M'`). These deliberately do NOT default to `Key.UP`/`DOWN`/`LEFT`/
`RIGHT` (the D-Pad's own fixed target) — the D-Pad's arrow-key
`setKeyDown()` calls happen outside the OR-merge pass, so sharing its
codes by default would let the OR-merge pass silently overwrite whatever
the D-Pad had just set that same tick.

## 6. Touch/mouse configuration

`[touch] enabled=`/`[mouse] enabled=` gate `Nintendo3DSInput::poll()`'s
existing touch→mouse translation entirely (both must be `true`; the 3DS
has exactly one pointer-like input source, so these two independently-
configurable flags gate the SAME path rather than two separate
mechanisms). `[touch] screen=` (`bottom`/`top`) selects which screen's
logical pixel dimensions `Nintendo3DSInput` is constructed with — `bottom`
(320x240) is the hardware-accurate default (the real touch digitizer is
only physically present on the bottom screen). This also fixes a
pre-existing Phase 10 quirk: the old embedded-demo app always passed the
TOP screen's dimensions regardless of which screen was actually touched
(documented in `Nintendo3DSInput.h`'s own header comment) — now genuinely
configurable instead of hardcoded.

None of `stageMouseX()`/`stageMouseY()`/viewport conversion/`InputState`
edge detection/hit testing were touched — this layer only supplies the
constructor arguments those existing mechanisms already accepted.

## 8. Replacing game.swf (hot-swap / recompilation independence)

**Verified this session, end to end:**

1. `romfs/game.swf` was swapped for a real, unmodified copy of "Hobo 2 —
   Prison Brawl" (~4.9 MB, SWF6/CWS).
2. `cmake --build build_3ds` was re-run — **zero C++ files were touched,
   and none were recompiled** (build log shows only the RomFS-packaging
   step re-running, not a relink of `flash3ds_3ds`).
3. The resulting `.3dsx` was re-parsed the same way as section 7, and its
   embedded `game.swf` entry matched the swapped-in Hobo 2 file
   byte-for-byte (`CWS` signature, 5,147,172 bytes).
4. `romfs/game.swf` was restored to the original clean-room demo content
   afterward, confirmed byte-identical via checksum.

**A real gap this test caught and fixed along the way:** the first
implementation packaged the `.3dsx` via a `TARGET flash3ds_3ds POST_BUILD`
custom command, which CMake only re-runs when the ELF itself relinks —
editing `romfs/game.swf` alone did NOT trigger repackaging, silently
leaving a stale `.3dsx`. Fixed by making packaging a proper
`add_custom_command(OUTPUT ...)` that explicitly `DEPENDS` on every file
under `romfs/` (via `file(GLOB_RECURSE ...)`), so a plain rebuild now
correctly picks up an EXISTING romfs file's changed *contents*. Adding a
**brand-new** file under `romfs/` (rather than editing an existing one)
still needs a re-configure to be picked up by that glob — a standard,
accepted CMake `GLOB` limitation, not something this build silently gets
wrong for the common case (swapping `game.swf`'s content).

**Runtime compilation is independent from SWF replacement**: no C++
source in this project references any specific game's content. The only
thing that changes when swapping games is `romfs/`'s contents (and,
per-title, `romfs/config.ini`'s `[game] swf=`/`[input]` values) — never
`src/`.

## 11. Known limitations

- No subdirectory support in the RomFS reader (flat root only — matches
  this project's own two-file layout; would need real hash-table-based
  directory traversal to extend, see `Nintendo3DSRomfs`'s own header
  comment).
- ~~`Nintendo3DSRomfs::open()` only supports a plain SD-card `.3dsx` launch~~
  — **superseded, see the 2026-08-24 addendum below.** `3dslink:/` and a
  non-homebrew-ABI fallback (`ARCHIVE_ROMFS`) are both implemented in the
  actual `Nintendo3DSRomfs.cpp` this section was originally describing;
  this bullet was never updated after that follow-up work landed. An
  NCCH/CIA launch path is still not implemented.
- Not independently verified on real hardware or an emulator this session
  (no device/emulator access) — verification was done by exhaustively
  cross-checking the produced `.3dsx`'s binary layout against the exact
  algorithm the ARM code implements (section 7) and against
  `docs/3ds-toolchain.md`'s own prior Phase-10 boot confirmation (Azahar)
  for everything this layer builds on top of unchanged.
- `[input]` remapping covers A/B/X/Y/L/R/ZL/ZR/START/SELECT/C-Stick
  (four directions) — the D-Pad/Circle-Pad's arrow-key mapping is fixed
  (see section 5). *(Updated 2026-08-24: ZL/ZR/C-Stick were added this
  session — previously only A/B/X/Y/L/R/START/SELECT were configurable.)*
- Config values are read once at startup; there is no live-reload of
  `config.ini` while the app is running.
